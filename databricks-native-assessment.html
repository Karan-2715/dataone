01
Executive summary

Feasible — and bigger than a port

DataOne is an application-tier "Agentic DBA": it connects to external OLTP databases and runs all query and data-movement work inside its own Python process. It has no compute engine, no lakehouse storage, and its own catalog and governance layer. Databricks provides exactly those three as first-class primitives. So the real question isn't "will it run" — it's "what do we stop owning."

Rough shares of the capability surface — directional, not audited. The through-line: delegate the infrastructure, keep the workflow intelligence.

The recommended path is phased, not big-bang: integrate with Databricks first, then run as a Databricks App governed by Unity Catalog, then push compute fully native only where it earns its keep. Each phase ships independently and is reversible.

02
Definitions

What "Databricks-native" can actually mean

"Native" is a spectrum, not a target. Each rung is a valid product, and they compound. The reversibility tag is the key planning input.

A

Databricks connector

DataOne stays standalone; adds a Databricks SQL Warehouse + Unity Catalog source/target alongside Postgres, MySQL, Oracle. New connector type only.

Fully reversible
B

Databricks App (Lakehouse App)

DataOne runs inside the customer's workspace; identity, secrets and network come from the workspace, governed by Unity Catalog. Auth + hosting re-platform.

Mostly reversible
C

Compute & storage native

Query + ETL pushed down to SQL Warehouses / Spark / DLT; landing zone is Delta in Unity Catalog. Rewrite of the execution and pipeline engine.

Hard to reverse
D

Marketplace / "Built on Databricks"

Validated listing + co-sell motion; layers on top of A/B/C. Packaging and validation, not code.

n/a

Recommendation: A → B → (selective) C, with D once B is stable. Rung A delivers most of the customer value for the least risk; C is only worth it where in-process Python is a real bottleneck.

03
Ground truth

The baseline we're re-platforming

Established from the code, not the marketing. Today's Databricks and Unity-Catalog mentions in the repo are aspirational copy — no code touches them. These are the couplings that collide.

No compute of its own

Query execution runs SQL through a native DB-API driver and does fetchall() in a thread, capped at 5,000 rows. No server-side cursor or streaming.

query_execution_service.py

ETL is in-process Python

Extracts in 1,000-row LIMIT/OFFSET batches, transforms row-by-row in Python, executemany-loads. Real movement only for sqlite / postgres / mysql.

pipeline_executor.py

No lakehouse concept

ETL lands in another OLTP DB. No Spark, Dask, Ray, Arrow, pandas or PySpark anywhere in the backend.

— absent by design —

App-owned catalog & governance

DataOne builds its own catalog, column profiles, classifications, lineage and semantic layer in Postgres.

schema_catalog_service.py · semantic_service.py

Orchestration = Celery + Redis

Celery workers, a Redis broker, Beat, and an in-process cron scheduler drive all async and scheduled work.

celery_app.py · scheduler.py

LLM = local Ollama, one swap point

Every AI call funnels through a single method behind a circuit breaker — provider-swappable by design.

ai_service.py · AIService.get_ollama_url()

Connectors = raw OLTP drivers

psycopg2 / pymysql / oracledb / sqlite3 plus a SQLAlchemy-URL "JDBC". No warehouse/lakehouse connector.

backend/app/connectors/

Auth & tenancy are thin

Local HS256 JWT + 3-role RBAC (admin/analyst/viewer), no SSO. Multi-tenancy is an unenforced nullable tenant_id placeholder.

rbac_service.py · models/pipeline.py

07
Strategy

The partnership — upside & the co-opetition trap

The partnership is the strategic prize and the strategic risk. Every feature we delegate is a feature Databricks could ship natively and commoditize. Read both columns before committing.

Upside

Why the partnership is worth pursuing

  • Distribution. Partner Connect + Marketplace reach every Databricks customer at lakehouse stand-up — a warm channel we don't have.
  • Credibility. A "Built on Databricks" badge shortcuts enterprise security review and procurement.
  • Aligned co-sell. Every DataOne query/pipeline burns DBUs — our usage is their revenue, so field teams have reason to bring us in.
  • Less to own. Delegating compute, storage, catalog and governance means less to build, secure, scale and certify — we ride their compliance surface.
  • Enterprise reach. Workspace identity + UC governance answer the SSO/RBAC/tenant gaps that are unbuilt in DataOne today — for free.

Risk

Why to phase it and hold the line

  • Commoditization. The DELEGATE column is exactly what Databricks is building — Genie, Lakeflow Designer, UC auto-classification. Build on them and our surface shrinks as theirs grows.
  • Platform lock-in. Rung C ties revenue and roadmap to one vendor's APIs and pricing.
  • Loss of our edge. Our differentiation is being multi-source and DB-agnostic. Going native risks narrowing to a single-platform tool.
  • Marketplace economics. Revenue share and listing terms compress margins — the channel isn't free.
  • Roadmap dependency. Delivery dates become hostage to Databricks feature availability and API stability.
The defensible position. Invest in the KEEP column — the agentic DBA workflow layer that sits above Databricks primitives: governed schema design/migration, cross-source mapping, human-in-the-loop autopilot. Treat Databricks as one powerful backend among several, never the whole product. Stay multi-source so we remain the layer that spans Databricks + everything the customer hasn't moved there yet — which is where migration and modernization work actually happens.
08
The call

Recommendation — phased and gated

The three framings reconciled: ship the low-risk integration now, earn each next rung with a go/no-go gate, and never let native ambition override the multi-source line.

Phase 1 · Integrate

Rung A

Ship the Databricks connector plus a Model Serving / Genie option. Databricks data becomes first-class in DataOne.

Go / no-go gateReal customer pull for Databricks data inside DataOne.
Phase 2 · App + delegate

Rung B

Run as a Databricks App with workspace identity; delegate catalog and governance to Unity Catalog. Pursue Marketplace validation.

Go / no-go gateB stable + partnership terms favorable.
Phase 3 · Selective native

Rung C

Push down only the pipeline/query workloads where in-process Python is a proven bottleneck. Don't rewrite on spec.

Go / no-go gateMeasured performance/scale need.

Throughout: hold the multi-source line. Databricks becomes the best-supported backend, never the only one. Spend engineering on KEEP, delegate the DELEGATE layer, and keep the phasing reversible.
